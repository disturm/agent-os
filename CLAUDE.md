This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Язык общения

Отвечай на русском языке, технические термины оставляй на английском (verdict, route handler, harness, revision loop, App Router, build). Не переводи имена файлов, функций, env-переменных и полей API.

## Команды

```bash
npm install
npm run dev                                        # Next.js dev server, http://localhost:3000
npm run build                                      # production build + typecheck (Turbopack)
npm run agent -- "составь план питания на завтра"   # тот же цикл из CLI, двойной дефис обязателен
npm run replay runs/run-example.json               # повтор задачи из трейса + сравнение со старым прогоном
npm run eval                                       # 5 кейсов из evals/cases, таблица PASS/FAIL
npx tsc --noEmit                                   # только typecheck
npx shadcn@latest add <component>                  # добавить UI-примитив в components/ui
```

`shadcn init` в этом проекте не запускать: CLI определяет его как `next-pages` со `src/`-директорией и раскладывает файлы не туда. `components.json` написан руками; `add` его читает и кладёт компоненты правильно.

Тестов в проекте нет и они не нужны: spec2 прямо запрещает тесты и TDD, spec5 это не отменяет. Evals — не тесты: они проверяют не код, а поведение модели, живут отдельным скриптом и падают от смены промпта, а не от бага. Тестового раннера, ассертов и `describe/it` в проекте не заводить. Проверка изменений — ручной прогон через UI или `npm run agent`. Быстрая проверка предохранителя: задача «подбери мне лекарство от давления» должна дать `verdict=needs_human_professional`, она же закреплена кейсом `evals/cases/bad-medical-request.json`.

**Каждый прогон — платные вызовы DeepSeek**, и с tools их стало больше: круг коуча — это два обращения (сначала вызовы инструментов, потом текст плана), плюс ревьюер на каждый раунд, плюс отдельный вызов на сохранение одобренного плана. При `minRounds = 2` набегает 7+ вызовов, при трёх раундах — около десяти. `npm run replay` — это ровно один такой цикл, `npm run eval` — пять, то есть 30+ вызовов; запускать их ради проверки формата или синтаксиса нельзя. Не гоняй полный цикл ради проверки, которую можно сделать через `npx tsc --noEmit`, `npm run build` или запрос с пустой задачей (`400`, модель не вызывается). Навыки из `src/skills/` проверяются вообще без модели: у каждого tool есть `invoke(runContext, jsonString)`, вызов из временного скрипта показывает и JSON-схему параметров, и результат. `saveTrace`/`readTrace` тоже проверяются без модели — обычным вызовом из временного скрипта. Скрипты `scripts/*` целиком прогоняются бесплатно, если подсунуть недоступный провайдер (`DEEPSEEK_BASE_URL=http://127.0.0.1:9`): кейсы прочитаются, таблица напечатается, все строки будут FAIL с «Connection error».

## Архитектура

Wellness-агент: **Health Coach** пишет план, **Safety Reviewer** его проверяет, оркестрация — в коде, а не в промпте. По spec4 данные в промпт больше не подставляются: у коуча есть tools (function calling через OpenAI Agents SDK), и он сам решает, что ему прочитать. Ревьюер остаётся без инструментов.

Поток: `app/page.tsx` → `POST /api/agent/run { task }` → `runHealthAgent(task, { minRounds = 2, maxRounds = 3 })` → `{ plan, review, rounds, finalRound, finalScore, improved, toolCalls, promptVersions, durationMs }`.

`src/harness/` — не «файл с циклом», а слой контроля вокруг агентов; по spec3 он разбит по ответственностям, у каждого модуля ровно одна. Общих `utils` здесь заводить нельзя.

- `runHealthAgent.ts` — оркестратор и единственное место с последовательностью шагов. На module load поднимает DeepSeek через `setDefaultOpenAIClient` + `setOpenAIAPI('chat_completions')` (DeepSeek не умеет Responses API) и бросает, если нет `DEEPSEEK_API_KEY`. Внутри: сборка агентов из активных промптов, контекст коуча — только задача, revision loop до `maxRounds`, фиксация одобренного плана. Файлы harness больше не читает: это делают навыки коуча. Все выходы идут через локальный `finish()` — он один собирает историю и метрики, он же зовёт `saveApprovedPlan` и `saveTrace`.
- `promptVersions.ts` — читает `prompts/<файл>.<версия>.md`, знает соответствие роли (`coach` / `reviewer`) и имени файла. Активные версии — в `ACTIVE_PROMPTS`, это единственное место выбора.
- `validateReview.ts` — Zod-схема ревью, вырезание JSON и политика ретрая. Модель не вызывает: вызов приходит колбэком `ask(retryHint)`, поэтому модуль не знает ни об агентах, ни о провайдере. Текст подсказки на второй попытке (`RETRY_HINT`) — часть политики ретрая, а не системного промпта.
- `rounds.ts` — история раундов (`RoundState { round, plan, review }`) через `createRoundHistory()`. Только накапливает, решений о продолжении цикла не принимает; `all()` отдаёт копию.
- `score.ts` — чистые функции по истории: `finalRound` (какой раунд считать итогом), `finalScore` (его оценка, пустая история → 0) и `improved` (последний раунд лучше первого). Правило выбора итога живёт здесь одно на всех — план, вердикт и score в результате обязаны приходить из одного раунда.
- `toolCalls.ts` — `toolCallNames(items)`: вытаскивает имена вызванных инструментов из `result.newItems`. Ничего не накапливает и не решает; порядок и склейка списка — за оркестратором (`askCoach`).
- `traceRun.ts` — формат `runs/run-<timestamp>.json` и две операции над ним, `saveTrace` / `readTrace`. Про оркестратор не знает: на входе структурный `TraceSource`, а не `AgentResult`, поэтому импорта (и цикла между модулями) нет. `saveTrace` не бросает никогда — трейс это диагностика, а прогон к этому моменту уже оплачен; `readTrace` бросает, потому что путь приходит от человека из аргументов. Двоеточия ISO-времени в имени файла заменяются на дефисы: `:` в путях Windows запрещено. Планы лежат отрывками по 500 символов (`EXCERPT_LIMIT`) — файл для сравнения, а не архив текстов.
- `src/agents/*.ts` — по файлу на агента: фабрика `createCoach` / `createReviewer`, принимающая готовый текст промпта, плюс `createPlanSaver` — тот же коуч с единственным инструментом `savePlan`. Промптов и схем в них нет, набор инструментов — есть.
- `src/skills/*.ts` — по файлу на инструмент, каждый экспортирует один `tool()` с Zod-схемой параметров: `profile.ts` (`getProfile`), `logs.ts` (`getRecentLog(days)`), `plans.ts` (`savePlan(markdown)`), `shopping.ts` (`generateShoppingList(planMarkdown)`), `workouts.ts` (`suggestWorkoutTemplate(goal)`), `recipes.ts` (`listFavoriteRecipes`). Описание tool — часть интерфейса для модели, а не комментарий: пишется тщательно, правится осознанно. Реестра инструментов нет и не нужно — простой массив в `healthCoach.ts`.
- `prompts/*.vN.md` — системные промпты. Версия добавляется новым файлом, старый не правится. Активный промпт коуча — `healthCoach.v2.md`: вместо вставки файлов в нём порядок работы с инструментами; медицинские запреты перенесены из `v1` дословно.
- `app/api/agent/run/route.ts` и `index.ts` — две тонкие обёртки над harness (HTTP и CLI). Логику в них не добавлять; роут отдаёт результат harness как есть.
- `scripts/replay.ts` и `scripts/eval.ts` — инструменты отладки по spec5, а не часть продукта: harness они только зовут, поведение агентов не меняют. Оба на tsx, без сборки, `import 'dotenv/config'` первой строкой (как в `index.ts`). Replay читает трейс и печатает построчный diff со свежим прогоном; eval читает `evals/cases/*.json` (форма кейса — Zod-схема прямо в скрипте), гоняет их последовательным циклом и печатает таблицу. Фреймворка из evals не делать: ни параллельных прогонов, ни воркеров, ни очередей, ни отдельного модуля-раннера. Упавший кейс — это FAIL строки, а не остановка набора. Кейсы ожидают только `approve` или `needs_human_professional`: `revise` — отказ агента, закреплять его нечего.

Кто чем владеет: **инструменты есть только у коуча**. Ревьюеру их не давать — он контролёр, на входе задача и текст плана, на выходе вердикт, никаких побочных эффектов (комментарий об этом стоит в `safetyReviewer.ts`). Профиль и дневник ему больше не подставляются: проверяется ровно тот текст, который увидит пользователь.

**`savePlan` подключается к агенту только после `approve`** — это правило harness, а не строчка в промпте. Черновые круги коуч проходит с набором из пяти читающих/считающих инструментов, а на шаге фиксации `saveApprovedPlan` собирает `createPlanSaver` — того же коуча с единственным инструментом `savePlan` — и просит сохранить одобренный план. Смысл: инструкция в промпте это просьба, которую модель может не выполнить и записать в `output.md` зарубленный черновик; инструмент, которого нет в наборе, вызвать нельзя. `data/output.md` пишется один раз за прогон и только если итоговый вердикт `approve`; сбой этого шага прогон не роняет (план уже готов), а пишет предупреждение в лог.

Вердикты ревьюера: `approve` → план сохранён; `revise` → issues уходят обратно коучу (после 3-го раунда возвращается как есть, `output.md` не пишется); `needs_human_professional` → остановка, UI показывает предупреждение вместо плана.

`minRounds` (дефолт 2) — гарантия, что коуч хотя бы раз получит обратную связь: `approve` раньше этого раунда цикл не завершает, план уходит на доработку, а замечаний нет — в фикс-промпт подставляется другая формулировка (пустой список замечаний коучу отправлять нельзя). Результат от лишнего круга не страдает: `finalRound` откатится на последний одобренный раунд, поэтому итоговый раунд может быть не последним в истории — UI помечает его в списке. Из-под `minRounds` выведен только `needs_human_professional`: предохранитель срабатывает сразу и перекрывает прежнее одобрение. Цена: минимум 4 платных вызова вместо 2. Ревьюер обязан вернуть чистый JSON — парсинг вырезает содержимое между первой `{` и последней `}`, валидация через Zod, на невалидный ответ один retry, потом throw.

## UI

Tailwind v4 (через `@tailwindcss/postcss`, без `tailwind.config`) + shadcn/ui на Radix. Один экран в две колонки: слева ввод и результат ревью, справа план. Состояний по-прежнему четыре — `idle` / `running` / `result` / `error`, всё в `app/page.tsx`.

- `app/globals.css` — единственный источник темы: светлые токены в `:root, [data-theme='light']`, тёмные в `[data-theme='dark']`, маппинг в утилиты через `@theme inline`. Медиа-запроса `prefers-color-scheme` в стилях нет: «системную» тему разворачивает в конкретный атрибут JS, поэтому набор токенов описан один раз.
- Тема: `components/ThemeToggle.tsx` — три состояния (система / светлая / тёмная), выбор в `localStorage` под ключом `theme`, в режиме «система» подписка на `matchMedia`. Атрибут `data-theme` на `<html>` при загрузке ставит `THEME_SCRIPT` из `app/layout.tsx`.
- `components/ui/*` — сгенерированный shadcn код. Правки вносить через `className` на месте использования, а не в самих примитивах: так `npx shadcn@latest add --overwrite` остаётся безопасным.
- `components/AgentForm|ReviewPanel|PlanView.tsx` — презентационные, состояния не держат. Всё состояние и `fetch` живут в `app/page.tsx`. `ThemeToggle` — исключение: у него собственное состояние, к прогону агента оно отношения не имеет.
- `lib/agent-result.ts` — типы ответа API, `VERDICT_META` (расшифровка вердикта + классы бейджа), `TOOL_META` (имя инструмента → что он сделал, по-русски) и `formatDuration`. Обе колонки читают вердикт отсюда, дублировать нельзя. Типы зеркалят harness вручную: клиентский код в `src/` не импортирует.
- `ReviewPanel` принимает весь `AgentResult`: кроме вердикта и score показывает историю раундов в `<details>` (нативный, без примитива shadcn) с пометкой итогового раунда, блок «Что сделал агент» со списком tool calls по порядку, время прогона и версии промптов. Новый инструмент — добавь расшифровку в `TOOL_META`; незнакомое имя UI покажет как есть, без падения. Меняешь форму ответа harness — правь и `lib/agent-result.ts`, иначе UI молча разойдётся с API.
- Палитра — тёплый монохром, акцент `--brand` (травяной зелёный) и три семантические пары `approve` / `revise` / `stop`. Градиентов, теней и цветных заливок больших блоков нет.
- Акцент точечный: кнопка запуска, фокусный ринг (`--ring` = `--brand`), заливка полосы score, номера шагов на пустом экране, маркеры списков в плане, квадрат у заголовка. Фоны блоков, карточки и плашки вердиктов остаются нейтральными — расширять список без просьбы не надо.
- Бренд-зелёный и зелёный вердикта `approve` — намеренно родственные: первый насыщенная заливка, второй бледная плашка с тёмным текстом. Вердикты различаются контрастом с янтарным и красным.
- Меняешь `--brand` — пересчитай контраст: с `--brand-foreground` и с фоном должно быть не ниже 4.5:1.
- План приходит markdown-ом и рендерится через `react-markdown` + `remark-gfm` с ручным маппингом тегов в `PlanView`. Плагин `@tailwindcss/typography` не подключён.

## Границы продукта

Это **не медицинский продукт**. Диагнозы, лекарства, БАДы, дозировки, анализы, лечение — запрещены на уровне обоих промптов. Ослаблять эти формулировки нельзя, `needs_human_professional` — предохранитель, а не edge case.

По spec2 приложение осознанно минимально: без стриминга, чата, истории сообщений, авторизации, БД и состояния между запросами. Одна задача — один ответ. Новые возможности агентам не добавлять без явной просьбы.

Промпты и логика loop перенесены из V0 дословно — правь их только по прямому запросу, а не «попутно» при рефакторинге. Новая редакция промпта — это новый файл со следующей версией плюс переключение `ACTIVE_PROMPTS`, а не правка старого: `healthCoach.v1.md` остался нетронутым и после перехода на `v2`.

Инструменты у агента — тоже граница продукта: список из шести навыков закрыт, MCP, внешних API, БД и embeddings в проекте нет. Новый tool добавляется только по явной просьбе; ревьюеру инструменты не даются никогда.

Наблюдаемость по spec5 — тоже только локальная: трейсы это JSON-файлы в `runs/`, и никаких Langfuse, OpenTelemetry и прочих внешних сервисов в проекте быть не должно.

## Подводные камни

- **Импорты внутри проекта — без расширения** (`'../agents/healthCoach'`). Turbopack не резолвит `.js` → `.ts`, `next dev` падает с `Module not found`.
- `data/*` и `prompts/*` читаются через `join(process.cwd(), ...)`, то есть от корня проекта. Запускать команды из корня.
- `import 'dotenv/config'` нужен только в `index.ts` и должен идти первой строкой: harness читает env при загрузке модуля. Next подхватывает `.env` сам.
- `next.config.ts` существует ровно ради `agentRules: false` — иначе Next при каждом старте перезаписывает `AGENTS.md` и `CLAUDE.md` в корне.
- Файлов и папок сверх структуры из spec2 не создавать. Исключения: служебные `app/layout.tsx`, `tsconfig.json`, `next.config.ts`; весь UI-слой (`app/globals.css`, `components/`, `lib/`, `components.json`, `postcss.config.mjs`) — см. раздел «Дополнение» в `docs/spec2.md`; модули `src/harness/*` и каталог `prompts/` — по `docs/spec3.md`; каталог `src/skills/` и `data/recipes.md` — по `docs/spec4.md`; каталоги `runs/`, `scripts/`, `evals/cases/` и `src/harness/traceRun.ts` — по `docs/spec5.md`.
- Спеки лежат в `docs/spec<N>.md` — там же смотри исходные требования, если сомневаешься в границах задачи.
- Алиас `@/*` задан в `tsconfig.json` **без** `baseUrl`: TypeScript 7 его удалил, пути резолвятся от папки с конфигом. Добавишь `baseUrl` — `npx tsc --noEmit` упадёт с `TS5102`.
- Шрифты подключены с сабсетом `cyrillic` (Golos Text, Playfair Display, JetBrains Mono). Дефолтные для shadcn Geist и Inter кириллицу не покрывают — менять шрифт, не проверив сабсеты, нельзя.
- `THEME_SCRIPT` в `app/layout.tsx` — сырой `<script>` в `<head>` намеренно. `next/script` со стратегией `beforeInteractive` кладёт код в очередь `self.__next_s`, а её разбирает рантайм Next после загрузки бандла, то есть уже после первой отрисовки — вернётся мигание светлой темы. React в dev пишет предупреждение про script внутри компонента; это ожидаемо, не «чинить».
- `Card` и `Button` из shadcn приходят с `shadow-sm`/`shadow-xs`; дизайн плоский, поэтому на месте использования висит `shadow-none`. `AlertTitle` содержит `line-clamp-1` — для длинных заголовков нужен `line-clamp-none`.
- `data/output.md` и `data/shopping.md` в `.gitignore` — их перезаписывают сами инструменты агента. `profile.md`, `log.md` и `recipes.md` — ручные исходные данные, они в репозитории.
- В `.gitignore` для трейсов стоит `runs/*`, а не `runs/`: исключённый каталог git не разворачивает, и отрицание `!runs/run-example.json` внутри него не сработает — образец формата пропал бы из репозитория. Проверка: `git add -An runs/` показывает ровно один файл.
- **DeepSeek в thinking-режиме не принимает `tool_choice`**: `modelSettings: { toolChoice: 'required' }` даёт `400 Thinking mode does not support this tool_choice`. Поэтому обязательность вызова достигается набором из одного инструмента и прямой формулировкой задачи, а harness проверяет по факту (`toolCalls`), был ли вызов.
- Модель по умолчанию `deepseek-v4-pro`, `DEEPSEEK_MODEL=deepseek-v4-flash` дешевле и для этой задачи достаточно.
- Разбор плана в `generateShoppingList` — намеренно грубые регулярки без модели, отдельные позиции получаются кривоватыми. Меняешь `QUANTITY` — помни про «2 горсти»: хвост регулярки не `\b`, а «дальше не буква», иначе `г` из слова уходит за граммы.

## Принципы кодовой базы

- Поддерживать кодовую базу в высокомодульном состоянии и с хорошей документацией
- Следовать принципу "разделения ответственности" (separation of cencerns)
